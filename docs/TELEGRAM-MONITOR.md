# Telegram: скачивания и звёзды MCRF

`.github/workflows/telegram-download-monitor.yml` опрашивает GitHub каждые пять
минут. При изменениях бот отправляет одно сообщение с тремя строками:
Windows, Android, движки; ниже — текущее число звёзд и его изменение, включая
отрицательное. Первый запуск присылает одно подтверждение включения с исходными
счётчиками, без выдачи старых скачиваний/звёзд за новые. Без изменений уведомления нет.

В 12:00 МСК отправляется итог за предыдущий московский календарный день
(00:00–24:00, UTC+3), в том числе с нулями. Пропущенный запуск догоняет
отчёты при следующем опросе. Первый день отмечен как неполный. При перерыве
более 15 минут отчёт предупреждает о неполных наблюдениях. Хранятся 35
суточных корзин; более старые пропущенные дни обозначаются как недоступные.

## Подключение

1. Через [BotFather](https://t.me/BotFather) создать бота, открыть с ним личный
   чат и отправить `/start` (либо добавить в нужный чат с правом отправки).
2. В GitHub → Settings → Secrets and variables → Actions добавить repository
   secrets `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` для проверенного получателя.
   Не сохранять токен в исходниках, URL команд, issue или логах.
3. Опубликовать скрипт, тесты и workflow в основной ветке репозитория
   `vnenapravo7-source/mcrf`. Разрешить Actions и встроенному `GITHUB_TOKEN`
   запись `contents: write`. Настройки защиты должны разрешать боту запись
   в отдельную ветку `telegram-monitor-state`.
4. В Actions запустить **Telegram download monitor → Run workflow**. Успешный
   первый запуск создаст ветку `telegram-monitor-state` с файлом
   `.github/telegram-monitor-state.json`. Придёт одно подтверждение с исходными счётчиками.
   Последующий рост счётчиков даст сообщение, первый суточный итог придёт
   на следующий день после 12:00 МСК.

Состояние содержит только ID/числа, даты, категории и счётчики звёзд; токен и
получатель туда не попадают. Основная ветка не получает коммит каждые пять
минут. Существующий workflow бейджей `update-download-counts.yml` независим.
Один concurrency group с `cancel-in-progress: false` исключает одновременные
запуски этого workflow; GitHub может заменить ожидающий запуск более новым.

## Что именно считается

Категории совпадают с существующими бейджами:

| Категория | Release asset |
|---|---|
| Windows | имя `mcrf.exe` без учёта регистра |
| Android | `.apk` в релизе с тегом `android-…` |
| Движки | все файлы каталога с тегом `engines-…`, включая метаданные/архив исходников |

Неучтённые типы файлов не входят в эти три категории. Разные имена APK,
включая alias, имеют собственные GitHub-счётчики. Черновики пропускаются.
Оба списка — релизов и файлов каждого релиза — опрашиваются с пагинацией.

Для каждого ID считается положительный прирост. Удаление файла не отнимает
уже замеченные скачивания; замена создаёт новый ID и включает его текущий
счётчик. Исчезнувшие ID сохраняются, чтобы возвращение файла не удвоило его
счётчик. При снижении счётчика того же ID отрицательное число не рассылается,
дальнейший рост считается от нового значения. Изменения звёзд — чистая разница
числа звёзд между опросами, а не перечень отдельных действий пользователей.

GitHub предоставляет накопленные `download_count`, без времени каждого
скачивания и без надёжного признака «обновление в приложении / вручную».
Бот честно указывает **«Источник: неизвестен»**. Для такого разделения нужны
отдельный backend учёта и обновление ссылок/клиентов, которые передадут
источник. Попытку запроса или редирект нельзя выдавать за завершённую загрузку.

Суточный итог — сумма замеченных разниц, отнесённых ко дню опроса. Разница,
накопленная во время перерыва или между опросами через полночь, попадает в
день следующего успешного опроса. Список GitHub не является атомарным снимком.
Поэтому распределение по суткам приблизительное. GitHub Actions может
задерживать/пропускать cron (особенно на границе часа); 12:00 — время, после
которого отчёт становится положенным, а не гарантия доставки ровно в секунду.
В публичных неактивных репозиториях расписание может отключиться через 60 дней.

## Ошибки и обслуживание

### Дополнительный учёт запросов по источникам

По умолчанию отключён. После отдельного развёртывания сервиса из
`docs/DOWNLOAD-SOURCE-TRACKING.md` задать repository variable `SOURCE_STATS_URL`
равной `https://vnenapravo7.ru/mcrf-downloads/v1/stats` и repository secret
`SOURCE_STATS_TOKEN` с тем же значением, что `MCRF_SOURCE_STATS_TOKEN` сервиса.
Другой URL, HTTP, параметры URL и перенаправления не допускаются. Токен не
попадает в состояние и логи.

Бот дополнит уведомления отдельной метрикой: **запросы вручную** по учтённым
ссылкам и **запросы в приложении** (включая установку движков), с тремя
категориями Windows/Android/движки. Они не сопоставляются с завершениями
GitHub, не доказывают уникальность, установку или появление нового
пользователя. Покрытие ограничено подключёнными ссылками и клиентами; события
могут быть повторными или поддельными.

Первое подключение и смена эпохи после сброса базы устанавливают исходную
точку без уведомления о старых запросах. Прирост считается по суточным
счётчикам, поэтому удаление старых дней из окна сервиса не отнимает новые
запросы. Суточный отчёт берёт именно предыдущий московский день из сервиса,
включая нули только в покрытом периоде и пометку первого неполного дня.
Предыдущие сутки до начала учёта/за пределами хранения недоступны.

Недоступность, устаревший ответ (более 15 минут), ошибка авторизации или
неверная схема сервиса **не блокируют монитор GitHub**. При переходе к ошибке
приходит одно сообщение «данные недоступны»; эта же пометка входит в обычные
уведомления и суточные отчёты. Старая исходная точка сохраняется для догоняющего
прироста после восстановления. Ошибка не подменяется нулевыми счётчиками.

### Основное состояние

HTTP/JSON ошибки, неверное состояние или Telegram `ok != true` завершают
запуск с ошибкой. Старое постоянное состояние сохраняется; токен, URL бота и
тела ошибочных ответов не печатаются. Следующий запуск повторяет наблюдение.
После успешной рассылки Actions сохраняет состояние отдельным коммитом.
Это доставка **как минимум один раз**: если сообщение ушло, а ответ/коммит
потерялся, следующий запуск может повторить его. Telegram `sendMessage` и
GitHub-коммит нельзя сделать одной транзакцией. Автоматических повторов
внутри отправки нет; при накопившихся отчётах Telegram может ограничить частоту.

Не удалять ветку состояния для обычного перезапуска: это создаст новую
исходную точку и потеряет промежуточные приросты. В существующей ветке отсутствие
или повреждение JSON считается ошибкой: восстановить файл из последнего
корректного коммита. Если нужно сознательно начать заново, сохранить копию
состояния, отключить workflow и только затем удалить ветку и включить заново.
Не запускать вручную параллельный экземпляр с тем же состоянием/получателем.

Локальная проверка без сети и без отправки сообщений:

```powershell
python -m unittest discover -s maintenance -p test_telegram_download_monitor.py -v
```
